# Capibara: инструкция для исполнителя «вбросов» (метрики из ноутбука + история изменений SCD2)

Документ самодостаточен: читай его первым, остальное — по ссылкам. Язык общения, комментариев в SQL и сообщений коммитов — русский.

## 1. Что за проект
Модель маркетплейса на датасете Olist (8 CSV, 09.2016–10.2018): из `raw` один SQL-скрипт собирает слои `core` (измерения и факты) и `mart` (витрины), поверх — API (FastAPI), поток событий (Redpanda + ingestor), ночная сборка (Airflow), дашборды Grafana. Чистый SQL, без dbt. PostgreSQL 16 в docker (`hack/hack`, БД `marketplace`, :5432). Проектные правила — `CLAUDE.md` в корне (обязательно прочитать целиком, он короткий). Требования — `docs/TZ.md`, `docs/architecture.md`, контракты — `docs/realtime/K0-contracts.md`.

## 2. Твоя задача (два блока)
**A. Новые метрики** (формулировки — в новом ноутбуке, который даст владелец; до его получения не гадай). Известно со слов владельца: история цены одного товара (выбрать товар, проданный по наибольшему числу разных цен, показать историю цены); доставка по штатам покупателя; воронка статусов заказа; оплаты и рассрочка. Каждая метрика = view в `sql/60_mart/` + строка в `sql/60_mart/650_metric_catalog.sql` (и при необходимости срез в `655_dimension_catalog.sql`) + панель в Grafana (`dashboards/grafana/json/`).
**B. История изменений (SCD2).** (1) Продавец/товар может сменить категорию товара: прошлые периоды должны остаться с прежней категорией. (2) Для любого заказа должен быть виден адрес покупателя на момент заказа, а не текущий. Заметка: в Olist `customer_id` уникален на заказ, поэтому адрес на момент заказа уже лежит в `raw.customers` по `customer_id`; а `customer_unique_id` — это человек. В исходных данных смен категории нет — история появится только из событий потока, если вы расширите контракт.

**Сначала ответь владельцу письменно на 3 вопроса и дождись решения, код не пиши:**
1. Версионировать только `dim_product` и `dim_customer` или ещё и `dim_seller`?
2. Откуда берётся история: только из событий потока (нужны новые типы событий, правка контракта и ingestor) или ещё синтезируется для демо?
3. Меняются ли ожидания Q1–Q5? (Golden-ответы менять нельзя без записи в `docs/decisions.md`.)

## 4. Правила проекта (выжимка из CLAUDE.md)
- Имена: snake_case, английские; `dim_`, `fact_`, `stg_`, `v_`; всегда со схемой.
- Деньги `numeric(12,2)`, моменты `timestamp`, флаги `boolean NOT NULL` (`is_`/`has_`); пустые строки → `NULLIF(TRIM(x),'')`.
- Покупатель = `customer_unique_id`. Выручка = Σ `price` по `dim_order_status.is_revenue` (delivered), без freight, месяц по purchase.
- Unknown-member `-1` в каждом измерении; JOIN только LEFT; строки не теряем; аномалии не правим — значения как в raw + флаги.
- Каждый SQL-файл начинается с шапки `object / grain / source / cc / why`.
- В `60_*` и `70_*` не должно быть `raw.`; без psql-метакоманд в `sql/`; без JOIN фактов разной гранулы без агрегации.
- Файлы нумеруются глобально, порядок сборки = порядок номеров: `00 setup → 05 landing → 10 seed → 20 staging → 30 dim → 40 fact → 50 constraints → 60 mart → 70 answers → 80 DQ → 90 grants`.
- Схемы `stg/core/mart` пересоздаются на КАЖДОЙ сборке (`DROP SCHEMA … CASCADE`). То, что должно жить между сборками, лежит в `landing` и `ops` (`IF NOT EXISTS`). История SCD2, которую нельзя пересчитать из raw, обязана жить в `ops`/`landing`, иначе сборка её сотрёт — обсуди с владельцем в вопросе 2.
- Гранты теряются при пересоздании схем, поэтому все — в последнем файле бандла (`sql/90_grants/`). Новые витрины читает роль `app_ro` (`GRANT SELECT ON ALL TABLES IN SCHEMA mart` уже есть в `900_grants.sql`).
- Витрины для Grafana — обычные `VIEW`, не `MATERIALIZED`. Запрос из Grafana обязан уложиться в `statement_timeout = 5s`.

## 5. Как работать (команды)
Сборка и тесты идут в docker. Основную базу `marketplace` НЕ ломай: её использует владелец.
```bash
DC="docker compose -f docker-compose.yml -f docker-compose.app.yml"
# своя база для проверок
docker exec hack_postgres psql -U hack -d postgres -c "CREATE DATABASE mp_scd2"
# полная сборка модели + DQ в своей базе (raw загрузится сам при первом запуске)
$DC run --rm -e PGDATABASE=mp_scd2 etl
# запрос к своей базе
docker exec hack_postgres psql -U hack -d mp_scd2 -c "select count(*) from core.fact_order"
# тесты (тесты, которым нужна БД, сами создают временную; нет БД — skip)
docker exec hack_app python -m pytest -q
# удалить свою базу, когда закончил
docker exec hack_postgres psql -U hack -d postgres -c "DROP DATABASE mp_scd2"
```
- Роли PostgreSQL общие на весь кластер: две сборки в разных базах одновременно могут упасть с `tuple concurrently updated`. Это не баг кода — просто повтори запуск.
- Не запускай `make reset`, `make demo`, `make down` и не останавливай контейнеры `hack_*`.
- Сборка `dist/build_model.sql` (только перед слиянием, по согласованию): `$DC run --rm --no-deps etl python -m pipeline.bundle`.
- Эталоны после любой правки модели не должны сдвинуться: выручка 13 221 498.11; средний чек 159.88; покупателей 96 096, вернувшихся 3.12 %; заказов 99 441; первый продавец 226 987.93; 24 месяца в Q1, 74 категории. Их проверяют DQ-проверки `Q1-CTRL…Q5-CTRL` и `DQ-01…12`: сборка в strict-режиме откатится, если что-то разошлось. Нужно 25/25 `[PASS]`.

## 6. Как устроены ключевые вещи
- **Измерения:** `sql/30_core_dim/` — `dim_customer` (300), `dim_seller` (310), `dim_category` (320), `dim_product` (330); у продавца и товара есть последняя колонка `is_inferred` (заглушки, которые создаёт ingestor, если событие пришло раньше справочника).
- **Факты:** `sql/40_core_fact/` — `fact_order`, `fact_order_item`, `fact_order_payment`, `fact_order_review`.
- **Витрины:** `605_v_sales_item` (позиции, основа большинства метрик), `610_order_summary`, `640_v_kpi`, `670–675` (платежи, доставка, покупатели, когорты, поток).
- **Каталог метрик:** `650_metric_catalog.sql` (код, формула, источник-view, допустимые срезы, аддитивность) и `655_dimension_catalog.sql`; из них работает API `/api/metrics` и `/api/query`. Новая метрика без строки в каталоге для API не существует.
- **Поток:** ingestor (`stream/ingestor/apply.py`) пишет в те же таблицы `core` upsert-ом, поэтому ЛЮБОЕ изменение структуры `dim_*`/`fact_*` (SCD2!) ломает ingestor, пока его не поправят. Менять ingestor ты не можешь — на каждое такое изменение составляй список «что нужно поправить в `stream/ingestor/apply.py`» и передавай владельцу. Тест сходимости: после реплея `core` должен совпасть с полной сборкой (md5 по таблицам) — не нарушай.
- **Cutoff (демо):** параметр `ops.build_params.cutoff` режет `stg` по дате покупки (`200–230`); новые staging-файлы должны учитывать его так же.

- Работай в своей ветке от `feat/realtime` (например `feat/scd2`), желательно в отдельном `git worktree`.
- Один коммит = одна законченная задача. Сообщение по-русски, conventional commits: `feat(SCD2): …`, `feat(метрики): …`, `fix(…)`, `docs(…)`. Без «wip» и серий мелких фиксов — правь до коммита.
- Коммить только свои файлы (`git add <пути>`, не `-A`/`.`). Нельзя коммитить: `.env`, `data/`, `output/`, `__pycache__`, `.DS_Store`, `.idea`, логи, дампы, временные и отладочные скрипты, закомментированный код, print-отладку.

- Новые Python-зависимости не добавлять (если очень надо — спроси владельца, с пином версии).
